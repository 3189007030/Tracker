# 隔离容量正确性门禁

`capacity_guard.rs` 是独立的标准库 HTTP/bencode 检查器，只能连接本机 `127.0.0.1:18081`，不依赖项目协议编解码器，不读取服务进程内存，也不连接返回的节点。它只验证隔离压测期间的指定属性；不证明公网路径、吞吐上限或长期稳定性。

该程序已由操作者在 S1 编译（Rust 1.99.1、拒绝警告）并通过无网自检；容量联动结果仍以 `benchmarks/capacity-guard.json` 为准，不能仅凭自检宣称通过。隔离实例需已启用测试用私有地址接纳，且与 filler 使用相同服务。勿将这个检查器接入生产实例。

## 构建与无网自检

在 Linux 的仓库根目录执行：

```sh
rustc --edition=2024 -D warnings -O validation/capacity_guard.rs -o /tmp/tracker-capacity-guard
/tmp/tracker-capacity-guard --self-test
```

预期自检输出 `{"stage":"self_test","ok":true}`，退出码为 0。自检不读取随机设备、不发网络请求；它覆盖 bencode 格式边界、重复字典键、候选集合过滤和内存拒绝格式。构建或自检失败即停止门禁，不得作为已验证结果。

## 协同执行

由具备管道管理能力的控制器启动 `/tmp/tracker-capacity-guard`，持续读取 stdout 并保持 stdin 打开。每个 JSON 行只含固定阶段名和布尔值；不要记录或输出原始请求、hash、节点地址或 peer ID。启动成功后依次执行：

1. 等待 `{"stage":"armed","ok":true}`。检查器已生成随机 hash H，登记端口 59000 和 59001 的两个模拟节点，验证双向互见及 scrape 中完整 1、不完整 1。检查器并不监听这两个端口，也不传输内容。
2. 由主代理启动和监测独立 filler，确认隔离实例确实到达**内存预算准入拒绝**。向检查器 stdin 写入 `check\n` 并 flush，等待 `{"stage":"check","ok":true}`。检查器在前后各做一次 scrape，确认 H 数量不变，两个现存节点均可更新并只看到对方；新随机 hash 必须收到 HTTP 200 的 bencode `memory budget reached` 业务拒绝，且拒绝内不含成功的候选和 interval、计数字段。其他拒绝、HTTP 错误或假成功均为失败。
3. 主代理停止 filler 后写入 `recover\n` 并 flush，等待 `{"stage":"recover","ok":true}` 与进程退出码 0。检查器停止两个节点，逐次确认 2→1→0，在同一 H 上重新登记一个节点并再清理，最后确认计数归零。

`check` 至多执行两次，且 `recover` 之前至少成功执行一次 `check`；最多接收三个命令。命令必须是完整的 `check` 或 `recover` 行。收到 EOF、输出管道失效、无效命令、超时或任一检查失败时输出固定的 `{"stage":"failed","ok":false}`，尽力停止两个原节点及可能被意外接纳的新 hash 节点，然后非零退出。清理请求本身也可能失败，不能据此假定远端状态已清除；隔离实例的 TTL 仍是兜底。

程序自启动起最多 600 秒，正常检查和等待保留最后 6 秒用于至多 3 个清理请求；每个 HTTP 请求含连接、写入和读取的总时限不超过 2 秒，累计应用请求和响应字节严格小于 256 KiB。它限制响应大小并拒绝分块响应和异常 Content-Length。若控制器异常终止检查器，来不及执行清理；不要将尽力清理误写成强制终止时的保证。

恢复步骤只要求原 H 成功复用，不要求任意新 hash 立即能够创建：删除后分片可能仍持有已分配容量。新 hash 拒绝是当次检查的内存准入证据，不代表所有后续请求都必定被拒绝。此门禁并不操作、停止或限速 filler，控制器必须单独约束和监控 filler。


## 结果边界

检查以具体时间点的固定 HTTP 业务响应和同一 H 的行为为证据。`check` 成功表明当次新资源请求被明确以内存预算拒绝，并且前后 scrape 计数和既有节点互见符合预期；它不证明整个压力期间所有节点都从未被驱逐，也不证明所有分片都无法接纳新请求。

全局预算耗尽时，另一个分片可能仍有已经计费的空闲槽位，因此某个新 hash 仍可能被合法接纳。此时门禁会报失败、尽力删除该测试登记；结果表示**此次门禁未达到预设的拒绝条件**，不能仅凭它判定 Tracker 的准入实现错误。控制器应结合 filler 的拒绝统计及测试条件独立判断，不得把任意限流、上限或传输错误当作内存预算拒绝。

`recover` 验证原 H 的停止、计数归零和同一资源在原分片上重新登记；它没有测量或证明总 RSS 已下降、保留槽位是否归还操作系统，或其他分片的准入已恢复。两个节点属于随机生成的测试资源，并未实现节点身份的长期持久性证明。
