## Capacity evidence

The first isolated S1 state sweep is saved in `benchmarks/state-initial.json`: 10k, 100k and 300k one-peer swarms were admitted. With a 768 MiB logical budget, 699,050 one-peer swarms were admitted before a truthful memory refusal; peak admission RSS was about 683 MiB. Cleanup completed and the process was not OOM-killed. This is in-process synthetic state measurement, not network throughput.

Matched 1024 MiB logical-budget sweeps are in `benchmarks/state-1024-*.json`. One-peer swarms reached 932,067 admitted nodes before a memory refusal, with roughly 998–1003 MiB admission RSS. Ten-peer swarms reached 1,847,152 nodes; 2,000 dense swarms admitted 2,000,000 nodes at about 457 MiB RSS. A 10,000-node hotspot was also admitted. A refused observer leaves delayed-discovery fields null, not passed. These earlier baseline cases measure admission-phase RSS, whereas the later scatter/churn reports also measure whole-run high-water and post-cleanup RSS.

Repeated swarm expansion and contraction exposed retained internal allocations. The fix and paired measurements are documented in [memory profiling](memory-profile-analysis.md): cumulative two-million-admission churn fell from about 243 MiB to 39 MiB RSS, while live dense scatter state remained essentially unchanged. These are controlled synthetic cases, not an assertion that all two-million-node workloads fit or that maintenance has a hard latency bound.

The completed network measurements include native IPv6 UDP targets of 100/200/400/800/1600/3200 requests per second, each with ten-minute stages above 99.9% protocol success. The earlier 6400/s target with a 1024-request window delivered only about 3991/s despite low server CPU, making that run measurement-limited rather than an S1 ceiling. In a later 600-second IPv6 UDP run with a 4096-request window and 6400/s target, 3,839,607 operations were attempted, 3,839,132 succeeded and 475 timed out (99.9876% protocol success); no one-hour confirmation was performed. These are individual network runs, not a guarantee of sustained capacity. `benchmarks/network-capacity.json` is a regenerable report; these values describe the snapshot generated at 2026-11-10 22:27:03 UTC.

In the completed local HTTP matrix snapshot updated at 2026-11-10 23:20:55 UTC, ten-minute IPv4 HTTP keep-alive and IPv6 HTTPS/UDP mixed runs each met the matrix qualification threshold at targets 100/200/400/800 operations per second. IPv4 new-connection runs at 100/s did not: HTTP achieved 94.4649% and HTTPS 99.5767% protocol success; the cause is not yet established. The matrix is dynamically updated, so later contents may differ from this recorded snapshot. A prior ten-minute 100/s IPv4 HTTP keep-alive run achieved 99.99% on the preceding engine before benchmark backend pooling was aligned with production. An IPv4 UDP short precheck had network-path losses despite zero server send errors and cannot qualify as a stable point. See [capacity measurements](capacity-report.md).

The independent [TCP path comparison](../benchmarks/tcp-path-comparison.json) completed, removed its temporary counters and verified unchanged native service identity. IPv4 HTTP and HTTPS new-connection diagnostics each completed 12,000 operations over 120 seconds; HTTP had 11,225 successes and 775 timeouts, HTTPS 11,926 successes and 74 timeouts. IPv6 HTTP completed 60,000 successful operations over 600 seconds and IPv6 HTTPS completed 59,999, all successful. SYN, SYN-ACK and RST are packet counts including retransmissions; they do not measure unique connections or establish the cause of a failure. The shorter IPv4 diagnostics are not ten-minute capacity grades.

The separate [IPv4 egress comparison](../benchmarks/ipv4-egress-comparison.json) used the verified proxy path for an HTTP new-connection target of 100/s. Of 59,438 completed operations over about 605 seconds, 28,706 succeeded and 30,732 timed out: 48.2957% protocol success, below the qualification threshold. The temporary route was restored. This single comparison does not establish a unique root cause.

The [isolated full-state guard](../benchmarks/capacity-guard.json) passed its armed, check and recover stages. At a 16,000/s target over approximately 120 seconds, it completed 1,911,122 operations, including 67,934 expected business refusals, with no timeout or invalid protocol reply. At refusal the engine reported 932,068 peer registrations, 932,067 swarms and 1,073,741,696 estimated bytes. The existing two peers remained mutually discoverable, scrape worked and the same resource recovered; isolated state was cleared and native service identity remained unchanged. This is a full-state correctness test, not a 96.45% success-rate capacity qualification. Lower RSS after the planned isolated reset is not an optimization result.

The [internal matrix](../benchmarks/internal-matrix.json) completed six distinct serial 600-second profiles, all with 100% protocol success and a combined 20,096,673 operations. The preceding `d427294a` source label applies to this matrix; the native binary was verified and remains unchanged in `a828e425`. The three IPv4 UDP profiles—dense, hot and cold—each targeted 8,000/s; IPv6 HTTP through isolated Nginx with new connections targeted 1,000/s; IPv4 HTTPS through isolated Nginx with new connections targeted 500/s; and mixed IPv4 HTTP/UDP announce/scrape targeted 8,000/s. The HTTPS stage achieved about 495.27/s. Generator and server shared S1's CPUs, private test addresses were enabled, and isolated state accumulated across stages. These six different profiles cannot be presented as a single constant-load one-hour run, a public end-to-end result or a server maximum.

The [full-state network run](../benchmarks/full-state-network.json) targeted 16,000/s on isolated IPv4 UDP loopback with two million synthetic registrations in 2,000 dense swarms. Over 600.022 seconds it completed 9,038,216 operations with 100% protocol success and about 15,063/s actual throughput. That is below 95% of the 16,000/s target, so this run does not qualify as a stable 16,000/s result. Full state was present for approximately 468.6 sampled seconds; generator and tracker shared two CPUs. It is not public throughput.

No S1 network ceiling, public one-hour capacity or 24-hour full-load figure is established. These longer tests were cancelled under the user's short-test policy, and the short passive observation is not 24-hour endurance evidence. The previous Python in-process simulations are historical evidence only.
