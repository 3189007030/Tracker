# Tracker 热路径与容量评估

范围为原生 Tracker 的 HTTP/UDP `announce`、`scrape` 和 UDP `connect`。Web 展示与观测采集各自运行，属于主机资源开销。时间使用 S1 UTC。

## 现有工作路径

1. HTTP/HTTPS 经 Nginx 进入原生服务。服务先限定并发和源地址请求速率，再解析 query。UDP 由 IPv4、IPv6 各一个收发循环处理，校验连接令牌后才进入状态修改。HTTP 与 UDP 写入同一套按 `info_hash` 分片的内存登记表。
2. 64 个分片分别加锁。一次通告会在锁内清理到期状态、更新登记、统计完成事件并选出其他节点。每个节点同时挂在分片过期索引和蜂群过期索引。查询能在有限清理预算内给出准确计数，耗尽预算时明确返回忙。
3. 现有实现已复用 UDP 连接令牌的 HMAC 状态、UDP 响应缓冲区和 HTTP bencode 编码逻辑。选点已限制尝试次数和返回数量。单个热门 `info_hash` 的处理仍串行于同一把锁内，多分片有助于分散不同蜂群的负载。

## S1 自然流量采样

2026-11-18 05:02:23–05:24:28 UTC，同一个原生 1.2.6 进程的两次只读快照相隔约 22 分钟。服务计时计数平均约 **994.5 次/s**，其中成功 `announce` 平均 **557.0 次/s**。HTTP `announce` 约 293.9 次/s，UDP `announce` 约 264.6 次/s，UDP `connect` 约 246.1 次/s，`scrape` 约 21.1 次/s。分项计数和计时计数口径不同。计时口径包括接收的 UDP 包和 HTTP Tracker 处理，不含网络往返或 socket 发送。

原生进程平均占用 0.113 个 CPU 核，RSS 约 405 MiB，状态估算约 494 MiB，同时登记约 65.1–65.7 万条，蜂群约 27.3–27.4 万个。两个采样点均无容量压力，计时桶差值 p95 上界为 500 μs。按观察到的端点总量计算，每个蜂群平均 2.38–2.41 条登记。平均值无法给出单节点和双节点蜂群占比。该窗口是自然流量观测。

## 候选优化

- HTTP announce/scrape 的普通参数借用原始字节，包含 `%` 和 `+` 的参数仍按原规则解码。保留未知参数的格式检查、重复键、长度和参数数量限制、错误优先级。
- 蜂群恰有两个登记节点且请求方仍在其中时，直接返回唯一有效的其他节点。`numwant=0` 提前返回，已停止或未登记的请求方仍遵循原有采样分支。
- 大蜂群选点以稳定的 slab ID 排除重复项。持有分片锁期间，同一蜂群内一个端点对应一个 ID；仍保留双栈、互补角色权重、尝试上限和总返回上限。

## 隔离验证

基线为 `v1.2.7` 的原生核心源码，与 S1 上 `v1.2.6` 的 Tracker 核心源码一致。S1 的临时网络命名空间仅启用回环。待测代码用 Rust 1.99.1 和同一套已缓存的工作区依赖编译，并固定单个 CPU、以低优先级执行。格式检查及 `-D warnings` 编译通过，`bt-protocol`、`swarm-engine` 和 `tracker-server` 定向测试合计 47 项通过。IPv4 和 IPv6 实例各自通过 HTTP↔UDP 双向互见、`numwant=0`、scrape 计数、停止后删除和清理检查。生产原生服务在试验前后均就绪。

HTTP 解析微基准按基线、候选、候选、基线交错运行。每个版本每种编码有 10 个计时样本，每个样本解析同一通告 150,000 次。表中时间为微秒/次的中位数。分配次数含重新分配，独立于计时进行统计。

| HTTP 查询场景 | 分配次数 | 基线 | 候选 | 耗时下降 |
| --- | ---: | ---: | ---: | ---: |
| 无转义 | 21 → 3 | 2.55 | 0.91 | 64% |
| 两个值各含一个转义 | 21 → 5 | 2.53 | 1.03 | 59% |
| 两个 20 字节字段全部转义 | 21 → 5 | 2.33 | 1.29 | 44% |

引擎基准预填同一蜂群，每个场景测 80,000 次重复通告。进一步用 A–B–B–A–B–A–A–B 交错八轮复核。表中为两轮实验的耗时下降范围，涵盖固定时间和按逻辑秒推进，`numwant=50`。

| 引擎场景 | 耗时下降 | 返回量 |
| --- | ---: | ---: |
| 双节点蜂群，IPv4 和 IPv6 各一个 | 31–36% | 每次 1 个 |
| 512 节点混合地址族蜂群 | 21–33% | 每次 50 个 |

整套 20 个场景合计的用户态加内核态 CPU 时间中位数下降约 24%，其中 512 节点且要求返回节点的场景占了主要工作量。3 节点、64 节点及部分 `numwant=0` 对照的计时方向在两轮间变化。主机同时处理自然流量，这些对照尚无稳定增益或退化结论。微基准衡量解析或引擎函数耗时，公网吞吐仍需按代表性负载测量。

复现入口为 `crates/bt-protocol/examples/http_parser_bench.rs` 和 `crates/swarm-engine/examples/announce_microbench.rs`。把相同的基准文件用于基线和候选。原始日志保存在工作区 `_tools/tracker-hotpath-check.log` 和 `_tools/tracker-hotpath-engine-confirm.log`。本次仅在工作区保留候选，完整发布门禁与线上切换尚未执行。

## 1–5 亿次每天的容量口径

| 每日请求 | 24h 均值 | 2 倍峰值示例 | 3 倍峰值示例 |
| ---: | ---: | ---: | ---: |
| 1 亿 | 1,157/s | 2,315/s | 3,472/s |
| 3 亿 | 3,472/s | 6,944/s | 10,417/s |
| 5 亿 | 5,787/s | 11,574/s | 17,361/s |
| 10 亿 | 11,574/s | 23,148/s | 34,722/s |

上表是负载设计数字。报表应同时给出入口总操作数、成功 `announce`、UDP `connect`、`scrape`、业务拒绝和超时；重试、未通过校验的包和成功登记会占用不同资源。峰值倍数要用实际 1 分钟和 5 分钟窗口校准。

若请求全部是成功通告，每条登记平均每 1,800 秒刷新一次，1 亿至 5 亿次每天对应约 208 万至 1,042 万条同时登记。S1 的有效配置上限为 200 万条登记和 1 GiB 状态估算预算。实际容量取决于有多少次请求是新登记、每个蜂群包含多少节点及过期和重登频率。过去的单节点蜂群合成状态测试约在 93.2 万条登记处触发预算，密集蜂群场景达到了 200 万条。按登记容量规划和按入口吞吐规划应各自验收。 [历史状态与网络试验](capacity-report.md)

## 验证下一档容量

1. 用真实汇总比例构造 HTTP/HTTPS 复用与新连接、UDP IPv4/IPv6、`connect` 与 `scrape`、`numwant=0`/非零返回。预填冷门、混合、密集和单热点四种状态，再注入正常刷新、停止和到期。记录每档实际发流、成功、拒绝、超时、p95/p99、CPU、RSS、UDP 内核丢包与维护耗时。
2. 用独立发流端逐档验证目标速率。发流量不足、客户端在途窗口饱和或链路先到顶时，将该轮标为测量受限。历史公网约 6,397 次/s、约 10 分钟的 IPv6 UDP 结果属于早期二进制和单协议；上线容量需针对候选与代表性混合负载重新验证。 [既有压测方法](benchmark-method.md)
3. 如果先遇到状态预算，优先测小蜂群紧凑索引和低并发情况下的保留容量。如果先遇到单族 UDP 丢包或单核饱和，再量化批量收发和 socket worker 的消耗。多机方案需按 `info_hash` 为 HTTP/UDP 路由到同一个负责人并验证互相发现，普通的独立状态轮询会拆开同一资源的节点表。

## 小蜂群端点索引候选

新蜂群含 1–4 个节点时，从已有的节点 ID 列表查找端点。第 5 个节点成功准入后建立哈希索引。曾建立索引的蜂群缩至 4 个时继续复用，缩至 3 个时释放。较大蜂群仍按原来的高水位机制紧凑索引。TTL、地址族、协议返回和逻辑准入常量沿用原规则。

以本报告 05:24 的线上聚合读数为例，65.1 万条登记分布于 27.4 万个蜂群。若计数视为同一快照，因为至少 5 节点的蜂群每个会比单节点蜂群多占至少 4 条登记，可得约 65% 的蜂群包含不超过 4 个节点这一估算下界。该计算无法推断有多少请求命中小蜂群。

内存基准沿用 `tracker-loadgen --state-bench` 并以上一轮解析和选点候选为基线。每轮在单独进程登记 120,000 条，再检查逻辑时间延迟下的节点可见性和过期清理。IPv4 固定时间、混合地址族分散到期、大蜂群对照使用相同的 256 MiB 逻辑预算和 Rust 1.99.1 工具链。比较清理前实际 RSS、进程内存高水位和逻辑准入估算。

刷新微基准初测的部分较大蜂群出现墙钟耗时上升。后续对每种场景以 A–B–B–A–A–B 单独进程复测，比较固定时刻与逻辑时间推进两段合计的进程 CPU 时间。每档每版本三轮，每段 75,000–350,000 次刷新。`numwant=50` 的 1、2、4 节点蜂群每次刷新 CPU 时间中位数分别下降 **13.4%、16.4%、15.7%**。5、8、64、512 节点场景的中位数从下降 2.5% 到上升 0.5%，未复现初测的大蜂群变慢。仍需用代表性线上规模验证混合负载与尾延迟。复测结果保存在 `_tools/tracker-compact-refresh.log`。在同一环境可用 `cargo run --release -p swarm-engine --example announce_microbench -- 350000 2 50` 选取单个场景。
