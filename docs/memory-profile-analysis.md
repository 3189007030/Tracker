# S1 状态内存与回收对比

以下是独立进程中的合成登记与逻辑时钟测试，不是公网吞吐、真实下载或全天容量证明。测试未向公开蜂群写入合成状态。逻辑准入预算均为 1024 MiB；测试进程由 systemd 限制为 1536 MiB、禁止交换。

| 同负载案例 | 修复前 RSS / 截至清理完成峰值 | 修复后 RSS / 截至清理完成峰值 | 已观测最长单次维护 |
| --- | --- | --- | --- |
| 累计 200 万次登记，蜂群依次扩容再缩成单节点 | 242.8 / 242.8 MiB | 38.6 / 38.7 MiB | 5.88 → 2.23 ms |
| 30 万条登记，3000 蜂群，分散到期时间及双栈角色 | 102.1 / 102.1 MiB | 102.3 / 102.3 MiB | 12.06 → 8.63 ms |
| 200 万条登记，2000 蜂群，分散到期时间及双栈角色 | 671.4 / 671.7 MiB | 674.9 / 675.2 MiB | 14.01 → 17.10 ms |

原始记录为 `benchmarks/memory-before.json`、`memory-after.json`。修复前使用保留的 Rust 引擎基线和同一新版测试程序；依赖、工具链、优化级别和主机保持一致。随机 hash 与分片种子每次变化，因此这些单次观测不能当作统计置信上界。

问题来自多个独立容器的历史容量：不同蜂群先扩大再留下一个节点时，蜂群 ids、端点表、蜂群到期桶和分片到期桶可能保留大分配，而全局 slab 又被下一批节点复用。修复在低水位时紧凑重建相关容器，保留索引次序和真实登记。端点表另记容量高水位，避免删除墓碑使 `capacity()` 变小而漏回收。

512 字节 peer / 640 字节 swarm 的保守准入常量保持不变。本次改善来自回收残留分配。分散到期案例的内存和维护开销也说明，真实时间分布必须纳入测量。

低水位重建按存活索引复制，发生在所属分片锁内。一个分片可能偏斜，单个到期桶也可能很大；不能由 64 分片推导硬性的均匀上界。上述 17.10 ms 是本次观测最大值，不是未来暂停保证。还需要协议压力下的延迟分位、实际多线程 RSS 和长稳记录。

先前 `state-1024-*.json` 的 `peak_rss_kib` 截止准入阶段；新版额外提供 `full_run_vmhwm_kib` 和清理后 RSS。逻辑估算清零不代表分配器或进程 RSS 清零。容量拒绝时无法准入验证观察者的逻辑互见字段可能为 null，不能改写为通过。
