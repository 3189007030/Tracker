# One-billion-requests-per-day envelope

This is capacity arithmetic and a preparation checklist, not a throughput promise or a completed test. It describes the current Rust code and the existing S1 measurements; the service's actual limit depends on the request mix, state, network, client behaviour and sustained load. The user stopped long-running tests, so no one-hour or 24-hour full-load qualification is claimed.

## Define the workload first

One billion requests in 24 hours averages **1,000,000,000 / 86,400 = 11,574.07 requests/s**. Peaks and bursts can be higher. Count the units explicitly: an HTTP announce, a UDP connect packet, a UDP announce, a scrape, a retransmission and a web/feed request are not interchangeable. If the target is one billion *successful announces*, UDP connects, scrapes, retries, invalid requests and other traffic are additional work. If the target is one billion total packets or mixed requests, fewer may be announces. An HTTP 200 containing a Tracker failure is not a successful announce.

At a steady rate, assuming **every accepted announce refreshes a distinct existing `(info_hash, IP, port)` registration exactly once per 1,800 seconds**, with no early repeats, changes of endpoint, stops or failed requests, the average active registrations required would be:

`11,574.07 × 1,800 = 20,833,333 registrations`.

This is neither a count of people nor an inference from the daily request total alone. One client can register multiple resources or endpoints; repeated or more frequent refreshes generate more requests per resident registration. The server advertises 1,800 seconds and a 300-second minimum, but these values do not prove that every client follows either interval. HTTP and UDP can refresh the same resource and endpoint registration; count the actual endpoint/resource pair, not a transport as a separate user.

For a different extreme, if every announce is a new distinct registration and none is stopped or refreshed, Little's law gives an illustrative required retained working set of `11,574.07 × 3,600 = 41.67 million` entries at the normal 3,600-second lifetime, assuming steady arrivals and departures and no admission limit. A persistent one-node swarm of self-reported seeds could use the 5,400-second small-swarm lifetime, yielding 62.5 million under that separate hypothetical. The code uses the longer lifetime only for a seed in a swarm with at most three peers, and timers are adjusted as the swarm changes; it is not a blanket lifetime. Actual churn, early stops, expiry backlog and refresh distributions change these estimates. Retention is not proof of peer reachability.

## State admission and host memory

The server's default configuration sets a 1,024 MiB logical admission budget, a 2,000,000 live-registration limit, a 2,000,000 swarm limit and a 10,000-peer-per-swarm limit. The standalone `EngineConfig::default()` has different smaller defaults; the server overwrites them with its settings. The current admission accounting charges **512 bytes per allocated peer slot and 640 bytes per allocated swarm slot**. Slots may be retained and reused after removal, so accounting can exceed `512 × live peers + 640 × live swarms`. It is an admission estimate, not RSS, and does not account for all process, kernel, Nginx, observatory, website and network-buffer memory. S1 has approximately 2,468 MiB physical RAM; the Tracker systemd unit sets `MemoryMax=1536M`, `MemoryHigh=1408M` and `MemorySwapMax=0`. Do not allocate all host memory to the engine or assume its accounting is a physical-memory reservation.

For a simplified fresh state with `k` registrations per swarm and no retained spare slots, `estimated bytes ≈ P × (512 + 640/k)`, subject also to the configured caps. Illustrative arithmetic with the 1 GiB budget:

| Shape | Arithmetic admission bound | At one refresh per 30 minutes per registration, illustrative refreshes/day |
| --- | ---: | ---: |
| 1 registration per swarm | about 932,067 registrations | about 44.7 million |
| 10 registrations per swarm | about 1,864,135 registrations | about 89.5 million |
| 100 or more per swarm | memory formula exceeds the 2 million configured live-peer cap | at most 96 million under this cadence and cap |

These are **state/cadence scenarios, not request-throughput ceilings**: the same bounded registrations can generate more requests through frequent refreshes, while new swarms and churn can exhaust admission earlier. A single hot swarm also hits the separate 10,000-peer cap. The 20.83 million-registration example is about 10.4 times the configured live-registration cap. Its peer-slot accounting alone is about **9.93 GiB**, before swarm slots, retained capacity and other memory; at one registration per swarm the combined estimate is about **22.35 GiB**, and at ten per swarm about **11.18 GiB**. All exceed S1's configured logical budget and the machine's physical memory. This conclusion follows from the stated cadence and accounting, not from assuming a billion requests means 20.83 million users.

The existing independent-state experiments recorded about 932,067 single-peer swarms before the logical budget stopped admission, and a dense case reached 2,000,000 registrations across 2,000 swarms. These were synthetic, distribution-dependent tests, not proof of a full-scale production working set. Under overload, measure real `rejected_*`, rate-limit and busy responses; do not turn a business failure into success or drop previously valid peers to fabricate capacity.

## Network and packet envelope

At 11,574.07 operations/s, each additional **1 byte of average wire traffic per operation** costs about **0.0926 Mbit/s** in the direction being measured and 1 GB per day. For a 200/512/1,024/2,048-byte average **combined ingress plus egress** per operation, the arithmetic is approximately **18.5/47.4/94.8/189.6 Mbit/s aggregate** and **200/512/1,024/2,048 GB per day**, respectively. These are examples, not S1 link speed or actual traffic measurements; calculate receive and transmit separately when evaluating a directional link. GB here is decimal. Add retransmissions, UDP connect exchanges, IP/TCP/TLS headers and handshakes, DNS, CDN/proxy behaviour, link overhead and other service traffic as appropriate.

For scale only, a standard 98-byte UDP announce plus IPv4 and UDP headers is 126 bytes at IP layer; a reply containing 50 IPv4 compact peers is 20 + 50×6 + 28 = 348 bytes, for 474 bytes combined. With IPv6, the corresponding 50-peer reply and IP/UDP headers gives 146 + 968 = 1,114 bytes combined. These examples assume full same-family peer sets, no extra headers, loss or UDP connect traffic; real replies may contain fewer peers. This implementation caps UDP replies at 50 peers and HTTP replies at 100; HTTP keep-alive, new TCP connections and HTTPS have different byte, packet and CPU costs. Measure bytes, packets and connection rates for the actual mix rather than extrapolating an empty response.

For unfragmented UDP announce exchanges, one inbound and one outbound datagram per operation would already be about 11,574 packets/s in each direction, before connect exchanges, retries or other traffic. At a hypothetical combined 1,024 bytes per operation, even an untouched 18 GiB active-test allowance would cover only about 1,631 seconds (27 minutes) at the daily-average rate; earlier testing and background traffic reduce the available budget. This arithmetic does not authorize or schedule a test.

## Existing evidence and next evidence needed

The existing public IPv6 UDP test at a nominal 6,400/s made approximately 6,397.23 attempts/s over about ten minutes with 99.9876% valid protocol replies. It is a short test on an earlier `d427294a`-era native binary and does not establish 11,574/s public capacity, a server ceiling, a one-hour capacity or a 24-hour capacity. A candidate using that same earlier native binary had an isolated same-host IPv4 UDP test with two million synthetic registrations, 2,000 dense swarms and about 15,063 attempts/s for 600 seconds; full state existed for only about 469 seconds, the configured 16,000/s target missed its 95% offered-rate gate, and client and service shared both CPUs. Loopback, synthetic peers and a short plateau cannot establish public capacity or day-long stability. Do not assume those binary results apply unchanged to a later build. See [the existing capacity report](capacity-report.md) and [full-state record](../benchmarks/full-state-network.json).

Without buying another server, useful preparation is to measure the real request mix and existing admission/overload reasons; profile parser allocations, shard contention, bounded peer selection, expiry backlog, UDP drops and TCP/TLS connection handling; and tune only against comparable, reproducible workloads while preserving genuine same-resource mutual discovery and truthful rejection. Reuse already measured aggregate counters, not raw client identifiers. Lower overhead or a different configuration might improve a particular workload, but it cannot make the 20.83 million simultaneously retained-registration scenario fit S1's current budget. Do not equate a restart's empty registry or a cold `numwant=0` test with a capacity gain.

A defensible future qualification needs independent load-generation and path verification, a representative cold/hot/mixed swarm distribution, real refresh/churn, populated peer replies and cross-protocol correctness. Record offered and completed rates, protocol-success and business-failure counts, p50/p95/p99, CPU, RSS, logical admission, accepted states and swarms, expiry backlog and maintenance delay, socket drops, connection rates, network bytes and packets per second. Distinguish short peaks, a measured sustained workload and any day-long observation. If the generator, source port space, link or approved traffic budget limits a run, report it as measurement-limited. A day-long capacity assertion requires evidence over that duration; none was obtained in the cancelled long tests. Any future test must follow the user's current short-test preference and the agreed public traffic budget unless the user changes those constraints.
